## 검사 변경과 재실행

`first-frame.spec.ts`는 대기할 때 매번 전체 프레임/재질 배열을 전송하던 대신 브라우저 안에서 대상 출현 여부를 계산해 boolean 하나만 반환합니다. 모든 render 호출의 ID/불투명도 표본은 계속 축적하며, 출현 후 전체 표본을 한 번 가져와 대상이 포함된 각 프레임의 ID 집합을 기존 기대값과 대조합니다. 표본을 줄이거나15초 기대 제한을 늘리지 않았습니다.

여성/CT 실패 시 렌더러 동일성·관찰 함수 유지·context loss 이벤트·프레임 예약 상태·보기 상태를 첨부합니다. 추가 조회도3초 안에 응답하지 않으면 그 사실을 기록합니다. 진단 자체가 응답하지 않는 상황을 ‘프레임0개’로 바꾸지 않습니다.

최종 첫 프레임 파일의 **3/3 검사(57.5초)**가 통과했습니다: 남성 네 계통 첫 표시43.4초, 여성/CT 다섯 전환8.9초, 취소한 다운로드의 늦은 출처 노출 방지4.9초. 전체 브라우저 회귀를 실행한 결과는 아닙니다. 별도 앞선 여성/CT3회 반복의 `.last-run.json`도 passed였지만 최종 근거는 직접 완료 출력을 확인한3/3 실행으로 한정합니다. 회귀 데스크톱/모바일 캡처를 직접 확인했고 `.cache/source-scheduling/regression-captures/`에 보존했습니다. 이전 역사 캡처를 새 결과로 덮어쓰지 않았습니다.

후속 Node 단위64/64와 앱 TypeScript 검사는 통과했습니다. TypeScript 설정의 대상은 앱 소스이며 브라우저 검사 파일의 별도 정적 타입 검사로 주장하지 않습니다. 런타임 변경이 없어 이번에는 로컬 프로덕션 빌드·전체 회귀를 반복하지 않았습니다.

## 렌더 제출 관찰

별도 진단은 같은 브라우저의 별도 페이지에서 남성34.5→68.5→80.5→88.5%를 먼저 표시한 뒤, 새 페이지에서 여성 최초 선택과 CT 왕복5회, 총11전환을 관찰했습니다. 브라우저 검사·캡처는 동시에 실행하지 않았습니다.

[최종 원시 기록](source-scheduling-report.json)은 `2026-09-21T08:45:17.572Z`에 시작했고,11전환 모두 대상 메쉬가 포함된 renderer 제출을 관찰했습니다. 렌더러·관찰 함수가 유지됐고 기록된 context loss/page error는0입니다. 클릭 시작부터 준비 문구까지156~871ms, 이후 표본 확인과 상태 조회까지 포함한 관찰 종료는319~1,818ms였습니다. 이 시간은 GPU 완료 시점이나 사용자 환경의 성능 보장이 아닙니다.

CT와 여성 장기 복귀에서 renderer의 geometry 수는 각각3/295로 반복됐고 texture는1이었습니다. 이는 해당 계수의 반복 관찰이며 메모리 누수 부재의 증명이 아닙니다. 그룹 자식1,220/11개와 실제 가시 제출 수는 다른 값입니다. `internal.frames=0`도 demand 방식이 쉬고 있을 때 정상일 수 있어 그 자체를 누락으로 판단하지 않습니다.

관찰기는 renderer를 감싸고 장면을 순회하므로 계측 부하가 있습니다. CPU render 호출 반환·가시 플래그 검사이지 GPU 픽셀 정확도 검사가 아닙니다. 준비 문구와 Canvas 상태 전환 전체가 원자적이라고 주장하지 않습니다. 이전 탐색 실행17전환과 남성 사전 표시 후11전환도 실패를 재현하지 못했으나, 도중에 진단기의 중첩 그룹 수집을 보완했으므로 최종 파일 해시가 있는 위11전환 기록을 재현 기준으로 삼습니다.
